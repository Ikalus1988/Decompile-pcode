# KAREL .pc 反编译语料库建设方案（调研 + 设计）

> 2026-11-01 实测盘点。结论先行：**可以建库，且建库是还原度从 77% 往 85%+ 走的最高效路径**。
> 语料三层（金标准配对 / 版本漂移 / 真实分布）+ 签名库 + 探针工厂，全部素材已在盘上。

### 1.3 关键结论

1. **库与现有配对语料是互补不是重复**：120 配对件中仅 4 个哈希出现在库（全在饰板）——
   JLR/M9 配对版是库外版本 → 去重后合并两不相厌，且天然产出"同名跨版本"漂移对。
2. **源码覆盖率**：106 个源码名中 63 个在库内有 ≥1 个二进制版本；库 211 名中 148 个无源码
   （name_map 跨实例映射的主战场）。
3. **%TEMP% 里的 jlr16_pairs 是唯一未被覆盖的 JLR 原件**——已复制到
   `Decompile-pcode-tests\corpus\jlr16_pairs\`（2.3MB，raw/src/dec 三件套）。⚠️ mifap_dec
   同理建议尽快并入（`%TEMP%\claude\mifap_dec`）。
4. **没有 .kl 源码在机器人备份里**（0 个）——备份只出编译件，金标准配对只能靠
   ①自有语料 ②KTRANS 支持库编译 ③探针工厂 三条腿。

## 2. 建库设计（目录约定 + manifest，不引入重型依赖）

```
D:\Downloads\Decompile-pcode-tests\corpus\
├── manifest.jsonl            ← 唯一事实源（一行一模块版本）
├── store\                    ← 内容寻址：store\<hash前2>\<hash>.pc（硬链接/复制一份）
├── pairs\                    ← 金标准（源码+编译件+dec+meta）
│   ├── jlr16\  m9_v174\  shipban\  mi04_deploy\  mi04_mifap\
│   └── compiled\             ← 探针工厂+KTRANS 支持库编译产物（随产随入）
├── drift\                    ← 同名多版本索引（name → [hash...]，标注每版是否有源码）
├── signatures\               ← core.ev 等解析产物（stdlib 签名 JSON）+ 各模块名字表 desc 抽取
└── reports\                  ← 度量基线快照（还原度随时间曲线）
```

**manifest.jsonl 每行**（模块版本级）：
`{name, hash, size, n_robots(拷贝数), versions_of_name(该名版本数), has_source, source_path,
 corpus(jlr|m9|shipban|…|compiled|library), pair_quality(同版|漂移|无源), gates(G1..G4),
 similarity{content,stmt,struct}, name_rate, known_gaps[]}`

**建库三步（按序执行，每步可独立验收）**：
1. **去重入库**：590 库件 + 116 库外配对件 → store/ 哈希寻址 + manifest 建档（一次脚本，~10 分钟）
2. **配对绑定**：106 源码名 ↔ 编译件按"同版优先、漂移标注"绑定；pair_quality 落档
3. **签名库解析**：36 个 .ev → signatures/stdlib.json（含形参类型码），并与模块名字表 desc 对账

## 3. 还原度提升项目的最高效保障机制

当前基线 **≈77%**（内容 78.4 · 语句 87.1 · 结构 54.3 · 名字 ~66 · 可编译 93）。提升路径按
**实测杠杆排序**（全部有量化依据）：

| 优先级 | 缺口 | 杠杆（实测） | 用库打法 |
|---|---|---|---|
| 1 | SELECT/CASE 只有注释级 | 结构 54→88（dcp_spr1_1 实测 67.4→88.3）→ 综合 +5~6pp | 探针工厂出 CASE 全形态探针（多值/ELSE/嵌套）；dcp_spr 系列 5 对金标准回归 |
| 2 | ~~FN 族 id→真名~~ **已完成（2026-11-02 续16）** | 饰板 G1 零错 40→**42**；24 id 全表落锤（fn_census 投票+T_FNS 探针；fn26=CNV_REL_JPOS 非 Sock_Send，旧 hex 键 14/15 误写十进制） | 打法实走：探针工厂 > 官方 .kl 反推（后者声明型居多，见 1.2 订正） |
| 3 | name_map 跨实例局部名 | 名字维度 66→80+（局部名 0→可读） | drift 层 98 个多版本名字做**跨实例槽位一致性验证**（同名不同版共用局部名映射） |
| 4 | 聚合拷贝 4b/4a/3c 词表 | 饰板剩 10 模块 51 错的大头；`基.字段=基2.字段2` 渲染 | 探针工厂 3 个探针落锤；库内真实分布抽 30 件验覆盖率 |
| 5 | 布尔字面量/零散强转 | 关键字维度 57.6→65 | 随手修，随 1 的回归带跑 |

**保障机制四件套**（比逐个修更重要）：
1. **基线冻结**：manifest 每字段可复算——`run_full_sweep + validate_sweep + run_shipban +
   test_similarity + test_known_names` 一键出报告，与 manifest 里的历史基线逐项 diff，
   回归=红。还原度百分比从此有账可查（本次 77% 是首个锚点）。
2. **探针工厂纪律**：每破一个缺口 = 一个最小探针（写源码→KTRANS→配对→入库 pairs/compiled），
   探针成为永久回归资产；官方支持库 21 个 .kl 先编一批撑覆盖面。
3. **缺口驱动 + 覆盖率度量**：对 706 件全量解压跑 opcode 直方图（diagnostics/dbg_unk_census
   现成），"未识别字节占比"就是词表缺口清单；每轮修完覆盖率必须升。
4. **漂移鲁棒性测试**：dcp_hist 9 版、mi01_cmn_rout 11 版 = 天然的锚点漂移考场——
   同一反编译器必须对全部版本产出可编译结果（行号锚点漂移是已知未处理项）。

**成本口径**：建库三步合计 ~半天（脚本化）；此后每轮改进的验证成本 = 一条命令。
不建库的代价 = 每轮手工确认语料完整性 + %TEMP% 丢失风险 + 还原度无账（本次盘点前
重合数两次算错：md5sum 文件名转义污染 hash 字段——**教训：哈希批量计算必须走
hashlib，shell 工具的转义会静默污染**）。

## 4. 风险与边界

- **%TEMP% 语料**：jlr16_pairs 已抢救；`mifap_dec`、`kl_probe` 残留、`jlr16_pairs` 原始位置
  仍建议尽快并库（%TEMP% 会被系统清理）。
- **无源码的 148 个名字**：只能做编译/零丢失/覆盖率验证，进不了相似度与名字度量——
  name_map 是唯一提升通道，不是 bug。
- **二进制入库纪律**：库≠仓库——store/ 不进 git（体量+许可），仓库只收探针源码与文档；
  manifest 与报告可进。
- 例程局部名的物理上限（.pc 无局部符号表）不因建库改变；库只能把"可复原的部分"拉满。

## 5. 验收判据（建库完成的定义）

1. `corpus\manifest.jsonl` 行数 = 706+，每行字段可复算对账；
2. 任意抽 10 行：hash→store/ 命中、has_source→pairs/ 命中、gates 字段能用现脚本复现；
3. 一键度量脚本输出 ≥77% 基线且与本表逐项一致；
4. %TEMP% 语料 0 依赖（删掉 %TEMP%\claude 后全链仍可跑）。
